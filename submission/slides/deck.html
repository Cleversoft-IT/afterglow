04 · why it's agentic

The model chooses tools, corrects itself, and exits explicitly.

1 · Self-correction on tool errors

Turn N: booking.create → validation_failed party_size required.
Turn N+1: re-read transcript, re-emit with party_size=4 → executed. Hard cap: 2 attempts per action.

2 · RAG-on-demand, not RAG-as-prefix

The agent decides whether to spend tokens on the Vector Store — and asks specific questions ("allergies on file?"), not catch-all queries. First-time caller: skip entirely.

3 · Explicit loop exit conditions

finalize → completed. max_turns → needs_review (first-class terminal, surfaced in the UI). error → failed. No silent fallback.

4 · Auditable turn-by-turn

Each turn → one audit row. Action results joined on payload.agent_turn (integer, not timestamps). The Agent Reasoning Trail is a first-class UI surface, not a buried log.

Real where it matters. Mocked where a multi-judge demo can't safely write.

REAL · billed on every call

  1. Speechmatics
    Batch STT on every uploaded MP3 · diarization on · language auto-detect · paid per minute.
  2. Gemini · Google ADK
    Multi-turn agent loop on every analyzed call · paid per token · no offline stub.
  3. Vultr RAG
    Non-zero input_tokens per query — verifiable live via /api/v1/admin/rag-probe.
Also real: Vultr Cloud Compute · Vultr Vector Store (preseeded + write-back in prod) · Vultr Managed Postgres · customer.update_profile mutates the row, undoable · Speechmatics TTS Preview generates every bundled and wizard MP3.

MOCKED · by design, not by absence

The outbound write-side integrations no public, multi-judge demo can safely fire. They have a typed contract; we just don't execute them against third parties during the hackathon.

booking.* whatsapp.* sms.* email.* calendar.* payment.* crm.* review.* RAG write-back (demo only)
Swap a mock for real = one entry in action_catalog.py + an env var. Not an architecture migration. The agent loop, the RAG, and the single-tenant deployment are production-ready today.
